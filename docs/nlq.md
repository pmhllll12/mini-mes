`POST /query`에 "최근 1시간 EQ-002에서 가장 많이 나온 불량 유형은?"처럼 질문하면, LLM이 **읽기 전용 도구**를 골라 호출하고 그 결과로 답합니다.
실무에서 "원하는 정보를 말로 묻고 싶다"는 불편함을 해결하려는 기능입니다.

![자연어 질의 응답 예시]({{ '/assets/images/nlq-query.png' | relative_url }})

*`POST /query` 응답 예시 (2026-09-30 평가에서 저장한 실제 응답을 질문 → 도구 호출(근거) → 답변 순으로 표시, 도구 결과는 설비 1개만 발췌). LLM은 SQL 없이 `get_daily_reports`만 골라 호출하고, 답변 수치는 도구 결과와 같습니다.*

## 설계 원칙

- **LLM은 SQL을 만들지 않는다.** 검증된 읽기 전용 도구 6개만 이름·인자로 골라 호출합니다. 조회 범위와 계산 방식은 기존 조회 API와 같습니다.
- **답변의 근거를 함께 돌려준다.** 응답에 호출한 도구·인자·결과를 모두 담아, 답이 어디서 나왔는지 사람이 확인할 수 있습니다.
- **키가 없어도 시스템은 동작한다.** API 키가 없으면 `/query`만 503이고 나머지 API·워커·모니터링은 영향이 없습니다.

```
질문 ─→ [LLM] ─ 도구 선택 ─→ [인자 검증] ─→ [조회 코드: OEE·불량·이상탐지] ─→ 결과
            ↑                                                                    │
            └──────────────────── 도구 결과 (최대 3라운드) ←────────────────────┘
   → 답변 + tool_calls(도구·인자·결과)
```

## 도구

| 도구 | 내용 | 재사용하는 코드 |
|---|---|---|
| `list_equipment` | 설비 ID·이름·라인·상태 (설비 이름만 언급된 질문에서 ID 확인용) | `/equipment` |
| `get_oee` | 기간 내 설비별 OEE·가동률·양품률·생산·불량 수량 | `/oee` |
| `get_defect_summary` | 기간 내 설비별·불량유형별 이벤트 건수·불량 수량 | `/quality/defect-summary` |
| `get_anomalies` | 기간 내 설비별 급변 이상 판정 수·최대 점수·최근 판정 목록 (설비당 20건) | `/anomalies` |
| `get_drift_alarms` (09-29 추가) | 기간과 겹치는 열화 경보: 설비별 경보 횟수·경보 중 여부, 경보별 시작·해제 시각·지속시간_초 (설비당 20건) | `/drift-alarms` |
| `get_daily_reports` (09-29 추가) | 저장된 일일 리포트를 날짜 범위(`YYYY-MM-DD`, 최대 31일)로. 리포트가 없는 날짜는 `리포트_없는_날짜`로 알려주고 **새로 만들지 않음** (읽기 전용) | `/reports/daily` (GET) |

- 수량·건수·시간 필드는 이름에 단위를 드러냅니다 (`품질이벤트_건수`, `불량수량_개`, `총생산_개`, `지속시간_초` 등). LLM이 불량 수량(개)을 건수로 말하던 문제의 대책입니다.

**안전장치**

- 설비 ID는 등록된 것만 (빈 배열이면 전체 설비). 없는 ID면 등록된 목록과 함께 오류를 돌려줍니다.
- 기간은 시간대가 있는 ISO 8601, start < end, 최대 30일.
- 잘못된 인자는 오류 메시지를 LLM에 돌려줘 스스로 고치게 합니다. 도구 호출은 최대 3라운드, 그 뒤에는 도구 없이 답변만 받습니다.
- 현재 시각(Asia/Seoul)을 질문과 함께 보내 "오늘", "어제", "최근 N시간"을 정확한 기간으로 바꾸게 합니다.
- 열화 경보 이력은 09-29부터 DB(`drift_alarm`)에 저장되어 `get_drift_alarms`로 조회합니다 (그 전에는 도구가 없어 "조회할 수 없다"고 안내하는 것을 평가했음).

## 제공자

요청의 `provider` → 환경변수 `NLQ_PROVIDER` → 키가 있는 제공자(claude 우선) 순서로 고릅니다.

| | Claude | Gemini |
|---|---|---|
| 기본 모델 | `claude-opus-5` | `gemini-flash-latest` |
| SDK | `anthropic` 1.8.0, 수동 tool use 루프 | `google-genai` 2.25.0, 자동 함수 호출을 끈 수동 루프 |
| 도구 정의 | `strict: true` (스키마에 맞는 인자 보장) | `parameters_json_schema` |
| 거절 처리 | 서버측 `fallbacks="default"` — Opus 5의 안전 분류기가 거절하면 추천 모델로 다시 실행 | 차단 응답을 `refusal`로 보고 |
| 재시도 | SDK 기본 2회 | `HttpRetryOptions(attempts=3)` |
| 검증 상태 | 미검증 (API 크레딧 없음) | 실제 API로 동작·평가 |

## 키 설정

- Docker Compose: `cp .env.example .env` 후 `ANTHROPIC_API_KEY` / `GEMINI_API_KEY` 입력. `.env`는 git에 올라가지 않습니다.
- Helm: 키를 values에 넣지 않고 Secret으로만 — `kubectl create secret generic mini-mes-llm --from-env-file=.env`. api 컨테이너가 Secret을 `optional`로 참조해, Secret이 없어도 파드는 정상이고 `/query`만 503입니다.

## 관측

- 메트릭: `mes_nlq_requests_total{provider, outcome}` (answer / max_rounds / max_tokens / refusal / error), `mes_nlq_tool_calls_total{provider, tool, ok}`
- Grafana "mini-mes 개요": "자연어 질의 요청 (최근 1시간, 제공자·결과별)", "자연어 질의 도구 호출 (최근 1시간)" 패널

## 평가

> **이 결과는 시뮬레이터가 만든 가상 데이터와 소수의 질문 기준이며, 일반적인 정확도를 뜻하지 않는다.**

`evaluate/nlq_eval.py`가 질문을 `/query`에 보내 채점합니다. 질문은 13개입니다. 09-29 도구 추가로 `drift_history`의 기대를 "조회할 수 없다고 안내"에서 "`get_drift_alarms` 호출"로 바꿨고, `daily_report_yesterday`를 추가했습니다. 바뀐 2개는 09-30에 평가했고, 아래 표는 **현재 13개 세트 기준**입니다 (변경 없는 11개는 09-28·29 결과, 2개는 09-30 결과).

- **도구 선택:** 기대한 도구가 성공으로 호출됐는가
- **인자:** 설비 ID와 기간(오늘·어제·최근 N시간, 허용 오차 10분)이 맞는가
- **근거:** 설비·기간이 맞게 호출된 도구 결과의 정답(최다 불량 유형, 이상 최다 설비, 09-30부터 열화 경보가 있는 설비 전부)이 답변에 그대로 들어 있는가. 데이터가 없으면 "없다"고 답해야 함
- **안내 문구:** 없는 설비·조회 불가 항목·범위 밖 질문을 추측 없이 안내하는가
- **언어 (09-29 추가, 모든 질문):** 한국어로 답했는가. 한글이 있고 한자는 한글의 1/5 이하 (로컬 모델의 중국어 답변 대응)
- **설비 언급 (09-29 추가, 설비를 기대하는 질문):** 답변에 나온 설비 ID가 기대 설비(전체면 등록된 설비)나 질문에 나온 ID뿐인가. 다른 설비를 해당 설비라고 말하거나 없는 ID를 지어내면 실패
- **설비 누락 (09-30 추가, 설비 언급 검사에 포함):** 비교 질문(기대 설비 2개 이상)은 기대 설비를 모두 언급해야 함. 로컬 모델이 "EQ-001과 EQ-003 비교"를 "EQ-003과 EQ-003"으로 답해도 기존 검사는 통과시켰음
- **필드 나열 (09-30 추가, 도구를 호출한 질문):** 도구 결과의 필드명(밑줄이 든 키, 예: `scored_count`) 3개 이상을 답변에 그대로 쓰면 실패. 로컬 모델이 질문에 답하지 않고 결과 JSON 구조를 설명한 답변이 설비 ID만 언급해 근거 검사를 통과했던 문제
- **단위 (09-29 추가, 불량 집계 질문):** 답변의 "숫자+건"/"숫자+개"가 도구 결과의 이벤트 건수/불량 수량과 맞는가. 불량 수량을 "건"으로, 이벤트 건수를 "개"로 말하면 실패 (숫자가 없으면 통과)

| 제공자 · 모델 | 평가 완료 | 통과 | 도구 선택 | 설비 인자 | 기간 인자 | 근거 | 안내 문구 | 평균 응답 |
|---|---|---|---|---|---|---|---|---|
| Gemini · `gemini-2.5-flash` | **13 / 13** | **13 / 13** | 11/11 | 10/10 | 10/10 | 4/4 | 2/2 | 4.7초 (09-28·29) |
| Claude · `claude-opus-5` | 미평가 (API 크레딧 없음) | | | | | | | |

- 무료 등급 하루 한도(모델당 20회, 질문 1개에 LLM 요청 2~3회) 때문에 **네 번에 나눠** 평가했습니다: 2026-09-28 8개, 09-29 오전 1개(`by_line`), 09-29 오후 3개(`compare_anomaly`, `unknown_equipment`, `out_of_scope`), 09-30 2개(`drift_history`, `daily_report_yesterday`). 실행마다 시뮬레이터 데이터가 다릅니다 (09-29는 DB를 새로 만든 뒤의 데이터). 09-28·29 답변은 이후 추가한 채점 규칙(단위·언어·설비 언급·필드 나열)으로 모두 다시 채점하지는 못했습니다.
- **09-30 새 질문 2개:** `daily_report_yesterday`는 3개 설비의 OEE·생산·불량(개)·최다 불량·급변 이상(건)·열화 경보를 리포트 값 그대로 답함. `drift_history`는 첫 실행에서 도구가 경보 11건을 돌려줬는데 **"열화 경보 이력이 없습니다"라고 답했고, 당시 채점은 이를 통과시켰습니다.** 도구 결과의 시각이 UTC(`06:28Z`)이고 조회 기간은 KST(`15:06~16:06+09:00`)라, 모델이 경보를 기간 밖으로 본 것으로 추정됩니다. 도구 결과의 시각을 모두 KST로 바꾸고, 채점에 "경보가 있는 설비를 모두 언급" 근거 검사를 추가한 뒤(첫 답변은 새 채점에서 실패) 같은 데이터로 재실행 → 11건을 설비별로 KST 시각과 함께 모두 전함. 1회 확인입니다.
- 설비 이름만 있는 질문("CNC 가공기 2호")은 `list_equipment`로 ID를 먼저 찾은 뒤 조회했고, 데이터가 없는 "어제" 질문에는 없다고 답했습니다.
- 없는 설비(EQ-009)는 도구 호출이 실패(`ok: false`)하자 수치를 지어내지 않고 "등록되지 않은 설비"라고 안내했습니다. 범위 밖 질문("내일 불량률 예측")은 도구를 호출하지 않고 예측할 수 없다고 답했습니다.

**답변 수치를 조회 API로 직접 대조**

- "최근 24시간 이상 최다 설비 EQ-003, 626건" (09-28) — API 값과 일치
- "최근 1시간 EQ-001 196건 중 95건(최대 10.0073), EQ-003 196건 중 115건(최대 14.4292)" (09-29) — API 값과 일치
- "오늘 EQ-002 최다 불량 dimension_out 217건, scratch도 217건으로 동일" (09-28) — **부정확.** 217은 불량 수량(개)인데 건수처럼 표현했고, 실제 이벤트 건수는 213 vs 204로 동률이 아닙니다.
- **재확인 (09-29, 코드 수정 없이 재실행):** "dimension_out으로, 125건이 집계" — **같은 오류 재현.** 실제는 이벤트 119건, 불량 수량 125개로, 수량을 건수처럼 말했습니다. 자동 채점(정답 유형 포함 여부)은 두 번 모두 통과해 이 오류를 잡지 못합니다.
- **수정 (09-29): 도구 결과 필드 이름에 단위를 드러냄.** `get_defect_summary`가 LLM에 돌려주는 필드를 `event_count`·`total_qty_defect` → `품질이벤트_건수`·`불량수량_개`로 바꾸고 도구 설명에 "서로 다른 값"을 명시했습니다 (조회 API `/quality/defect-summary`의 응답 형식은 그대로, 시스템 프롬프트는 바꾸지 않음). 새 데이터(시뮬레이터 3분 추가)로 `defect_top_today`를 2회 실행 → 두 번 모두 "dimension_out으로 127**개**"로 단위를 맞게 답함 (DB: 이벤트 121건, 불량 수량 127개). 같은 데이터로 2회라 개선의 근거이지 완전한 해결의 증거는 아닙니다.
  - 정정: 09-28 문서의 "시스템 프롬프트에 '건수와 수량 구분'을 넣는 개선"은 제안이었고 코드에 들어간 적이 없습니다. 09-29에 이를 적용된 수정으로 잘못 읽고 "프롬프트 문구로는 해결되지 않음"이라고 적었다가 바로잡았습니다.

## 로컬 모델 (Ollama, OpenAI 호환 어댑터)

`NLQ_PROVIDER=openai_compat` (또는 요청의 `provider`)이면 OpenAI Chat Completions 호환 API를 씁니다. 설정은 `OPENAI_COMPAT_BASE_URL`·`OPENAI_COMPAT_MODEL`(키는 선택)뿐이라, 로컬 Ollama·OpenAI·Groq·OpenRouter 등을 설정만 바꿔 쓸 수 있습니다. SDK 없이 `requests`로 호출합니다. 목적은 **무료 한도 없이 평가를 반복**하고, **데이터를 외부로 보내지 않는 구성**(온프레미스)을 확인하는 것입니다.

- 환경: RTX 3050 8GB, WSL의 Ollama. API 컨테이너는 `host.docker.internal:11434`로 접속
- `qwen3:4b` (tools 지원 표시): 인자가 필요한 도구 호출을 정식 `tool_calls`가 아니라 **본문 텍스트(JSON)로 출력**해 실행되지 않음. 생각 과정 끄기(`reasoning_effort=none`, Ollama `think:false`)로도 같음, 요청당 50~90초 → 평가 대상에서 제외
- `qwen2.5:7b-instruct` (VRAM 4.7GB, 전부 GPU): 13개 질문 전체 평가 (09-29, 질문 13개 세트)

|---|---|---|---|---|---|---|---|---|
| openai_compat · `qwen2.5:7b-instruct` (로컬) | 9 / 13 | 7/11 | 6/10 | 6/10 | 2/3 | 1/1 | 2/2 | 5.0초 |

- **실패 4개:** 3개는 인자는 맞았지만 도구 호출을 깨진 텍스트(`olith {"name": ...} </tool_call>`처럼 앞뒤에 쓰레기 문자)로 출력해 실행되지 않음. `by_name`은 `list_equipment` 없이 설비 ID를 `CNC-2`로 추측, `by_line`은 없는 ID(`EQ-B1`, `EQ-B2`)를 지어낸 뒤 오류를 받고 "LINE-B 설비는 EQ-001~003"이라고 틀리게 답함 (실제 EQ-003)
- **통과했지만 문제:** `anomaly_top_24h`는 **중국어로 답했고** `anomalies_omitted`(목록에서 생략한 건수)를 "무시된 이상"으로 잘못 해석. 채점이 답변 언어·필드 해석까지는 보지 않음 (09-30 필드명 수정, 아래)
- 잘 된 것: 새 도구 `get_drift_alarms`로 설비별 경보를 정리, 데이터 없는 "어제"는 없다고 답함, 없는 설비·범위 밖 질문은 추측 없이 안내
- **언어·설비 언급 검사 추가 후 다시 채점 (저장된 답변, 모델 재호출 없음):** 8 / 13. `anomaly_top_24h`(중국어 답변)가 새로 실패로 잡히고, `by_line`(틀린 설비 언급)은 원래 실패. 같은 방식으로 Gemini 09-29 답변 7개를 다시 채점하면 모두 통과 (09-28 답변 8개는 파일이 남아 있지 않아 다시 채점하지 못함)
- **필드명 수정 후 (09-30):** `anomalies_omitted` → `목록에서_생략된_이상_건수`(열화 경보의 `생략된_경보_수`도 `목록에서_생략된_경보_수`로 맞춤). 이상 질문 2개를 4회 실행한 답변 8개 중 이 필드를 언급한 4개가 모두 "목록에서 생략된"으로 읽었고 한 번은 "458건 중 생략 438건"으로 수치도 맞음, "무시된"으로 해석한 답변 없음. 13개 전체 재평가는 6 / 13으로, 실패 원인은 필드 해석이 아니라 기간 인자 오류(최근 1시간을 25시간으로), 중국어 답변, 질문에 답하지 않고 도구 결과 JSON 구조를 설명하는 답변(이상 목록이 긴 `get_anomalies` 결과에서 반복), 설비 혼동(EQ-001과 EQ-003 비교를 "EQ-003과 EQ-003"으로)이며, 같은 모델의 실행 간 편차가 큼(09-29 9 / 13). 설비 누락·필드 나열 검사를 추가해 같은 답변을 다시 채점하면 5 / 13 (`anomaly_top_24h`의 구조 설명 답변이 새로 실패). Gemini 09-29 답변 파일은 남아 있지 않아 새 검사로 다시 채점하지 못함
- **판단:** 빠르고 한도가 없지만 도구 호출 형식 오류와 ID 추측·조작이 있어 서비스용으로는 부족. 개발 중 빠른 반복 확인용. 깨진 형식을 고쳐 읽는 모델 전용 우회 코드는 넣지 않음

### 로컬 모델 비교 (2026-10-01)

8GB GPU에 들어가고 Ollama에서 도구 호출을 지원하는 8B급 모델 3개를 추가로 평가했습니다. 같은 날, 같은 채점 규칙(13문항, 설비 누락·필드 나열·언어 검사 포함)으로, 기준선인 `qwen2.5:7b`도 다시 실행했습니다. 데이터는 실행 중인 시뮬레이터 데이터라 모델마다 조금씩 다르지만, 채점은 각 응답이 받은 도구 결과를 기준으로 합니다. 모델당 1회 실행입니다.

| 모델 (Ollama, 모두 100% GPU) | 통과 | 도구 선택 | 설비 인자 | 기간 인자 | 근거 | 설비 언급 | 언어 | 평균 응답 |
|---|---|---|---|---|---|---|---|---|
| `qwen3:8b` | **12 / 13** | 11/11 | 10/10 | 10/10 | 4/4 | 9/10 | 13/13 | 46.4초 |
| `llama3.1:8b` | 7 / 13 | 7/11 | 6/10 | 4/10 | 1/4 | 9/10 | 13/13 | 6.5초 |
| `qwen2.5:7b-instruct` (기준선) | 6 / 13 | 8/11 | 7/10 | 6/10 | 1/4 | 8/10 | 10/13 | 5.5초 |
| `granite3.3:8b` | 1 / 13 | 0/11 | 0/10 | 0/10 | 0/4 | 10/10 | 13/13 | 8.3초 |

- **`qwen3:8b`:** 도구 선택·인자·근거가 모두 맞고 한국어로 답해, Gemini(13/13)에 가장 가깝습니다. 같은 계열의 `qwen3:4b`는 도구 호출을 텍스트로 출력해 실패했는데, 8B는 정식 `tool_calls`로 호출했습니다. 실패 1개(`compare_anomaly`)는 EQ-001·EQ-003으로 올바르게 조회하고도 답변에서 EQ-001을 **EQ-002로 잘못 적은** 설비 혼동입니다. 대신 답변 전에 생각 과정을 길게 생성해 평균 46초가 걸립니다(모델은 전부 GPU에 올라가 있음).
- **`llama3.1:8b`:** 한국어는 안정적이지만 기간 계산("오늘", "최근 24시간")을 자주 틀리고(4/10), 설비 이름·라인으로 물으면 `list_equipment` 없이 답하며, 열화 경보·일일 리포트 질문에는 도구를 호출하지 않았습니다.
- **`granite3.3:8b`:** 도구를 한 번도 호출하지 않고 `await list_equipment()` 같은 코드를 **본문 텍스트로 출력**했습니다 (`qwen3:4b`와 같은 실패).
- **판단:** 로컬(온프레미스) 구성이 필요하면 `qwen3:8b`가 유일한 후보입니다. 다만 1회 실행이라 편차를 모르고(`qwen2.5:7b`는 실행 간 9/13 ~ 5/13), 응답이 46초라 채팅 화면에는 느립니다. 서비스 기본값은 Gemini를 유지합니다. 다음 확인: 생각 과정을 끈 `qwen3:8b`의 정확도·속도, 반복 실행 편차
- 평가 중 발견: Windows에 별도로 실행된 Ollama(0.35.0)가 11434 포트를 먼저 잡으면 API 컨테이너의 `host.docker.internal:11434`가 그쪽으로 연결돼 모든 질문이 404(모델 없음)가 됩니다. Windows Ollama를 종료한 뒤에도 WSL 포트 중계가 돌아오지 않아, 평가는 `OPENAI_COMPAT_BASE_URL`을 WSL IP로 덮어써 실행했습니다(WSL IP는 재시작마다 바뀌어 `.env`에 고정하지 않음)

## 실제 API로 발견한 문제

| 문제 | 원인 | 조치 |
|---|---|---|
| 도구 결과를 보내는 두 번째 요청이 400 | 함수 결과를 `role="tool"`로 보냄 (SDK README 예제). Gemini Developer API는 `Role 'tool' is not supported` | `role="user"`로 전송, 단위 테스트에 반영 |
| 간헐적 503 | Gemini 서버 일시 과부하 (09-30 16:00~16:03에는 재시도 3회도 모두 503) | 408/429/5xx 재시도 (최대 3회), 몇 분 뒤 다시 평가 |
| 경보가 있는데 "없다"고 답함 (09-30) | 도구 결과 시각은 UTC, 조회 기간은 KST → 모델이 시간대를 무시하고 비교한 것으로 추정 | 도구 결과의 시각을 KST로 변환 (조회 API 응답은 그대로), 채점에 열화 경보 근거 검사 추가 |
| 평가 중 429 연속 | 무료 등급 하루 한도가 모델당 20회. 질문 1개에 LLM 요청 2~3회 | 평가 스크립트에 질문 간 대기(`--delay`), 한도가 별도인 모델로 평가 |
| 채팅 화면에서 질문을 연달아 보내면 `502 Gemini API 오류 (HTTP 429)` (10-01) | 무료 등급 한도(분당 또는 하루) 초과인데, Gemini 응답의 한도 종류·재시도 대기를 버리고 502로 돌려줌 → 사용자도 로그도 원인을 구분할 수 없음 | 제공자 429는 `/query`도 429, 응답의 `quotaId`(PerMinute/PerDay)와 `retryDelay`로 안내 문구 생성, 서버 로그에 남김 |
| Cloudflare Tunnel 공개 후 채팅 화면에 Cloudflare 오류 페이지 HTML이 통째로 출력 (10-02, 시연 영상 녹화 중) | Gemini 일시 과부하(503, 재시도 3회 모두 실패)를 `/query`가 502로 돌려주는데, Cloudflare는 origin의 502/504를 자체 오류 페이지로 바꿈 → detail이 사라지고, 채팅 화면은 JSON이 아닌 본문을 그대로 출력 | 제공자 오류는 503으로 (Cloudflare가 그대로 전달), 채팅 화면은 JSON이 아닌 오류 응답이면 짧은 안내만 표시 |

## 채팅 화면과 공개 서버 남용 방지

- `/chat`(`/`도 여기로): 질문 입력 → `/query` 호출 → 답변과 **근거(도구·인자·결과 표)** 를 펼쳐 볼 수 있게 표시. `api/static/chat.html` 정적 페이지 하나(외부 라이브러리 없음), 답변의 간단한 마크다운(굵게·코드·목록)만 처리하고 HTML은 이스케이프
- 방문자가 직접 써 볼 수 있게 서버에서 공개하되, 무료 한도(Gemini 하루 20회)를 지키기 위해 세 겹으로 막습니다.

| 장치 | 위치 | 동작 |
|---|---|---|
| IP당 rateLimit | Traefik Middleware (`POST /query`만) | 분당 약 3회, 넘으면 429 |
| 하루 상한 | api `NLQ_DAILY_LIMIT` (서버 8, 기본 0=없음) | KST 날짜별 질문 수, 넘으면 429와 초기화 시각. 남은 횟수는 `GET /query/quota`로 채팅 화면에 표시. 제공자 설정이 없어 503인 요청과 제공자 오류(Gemini 503 과부하 등)로 답을 못 준 질문은 세지 않음 (10-06: Gemini 503 두 건이 방문자 몫을 깎던 문제 수정). 제공자 5xx는 "잠시 뒤 다시 시도" 안내로 표시 |
| 제공자 고정 | api `NLQ_ALLOWED_PROVIDERS` (서버 `gemini`) | 요청 본문의 `provider`로 다른 제공자를 고르면 403 |

- 하루 8건: 질문 1건에 보통 2회(도구 호출 1회 + 답변), 최대 4회 호출 → 방문자 몫을 제한해 평가용 여유를 남김 (평가도 같은 `gemini-2.5-flash` 한도 사용)

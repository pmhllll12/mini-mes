> **이 결과는 시뮬레이터가 만든 가상 데이터 기준이며 실제 설비 성능이 아니다.**

## 구조

`anomaly-worker`는 API와 분리된 별도 컨테이너입니다.

- **특징:** 생산실적 1건당 사이클타임, 구간당 생산 수량(`qty_good + qty_defect`), 불량률
- **모델(v2):** 설비별 Isolation Forest + 범위 이탈 robust z-score
  - `anomaly_score = max(if_score / if기준, z_score / z기준)`, `z_score` = 특징별 `|x - 중앙값| / (1.4826 × MAD)`의 최댓값
  - 두 기준과 최종 threshold는 모두 학습(정상) 데이터 점수의 99% 분위수 → 학습 범위 밖으로 멀어질수록 점수가 계속 커짐
  - `if_score = -score_samples()`, MAD가 0이면 표준편차로 대체. v1(Isolation Forest 단독) 모델 파일도 그대로 판정 가능
  - 옵션 `train.py --rolling-window K`: 최근 K구간 사이클타임 중앙값·합산 불량률 특징 추가 (아래 C안, 열화 경보에 사용)
- **워커:** 10초마다 아직 판정하지 않은 최근 24시간 생산실적을 추론해 `anomaly_result`에 기록
  - `anomaly_result`에 log_id가 없어(스키마 변경 없음) 생산실적의 `ts`를 그대로 쓰고, `(equipment_id, ts)`로 중복 기록을 막음
  - 학습에 쓴 구간(`train_end` 이전)은 추론하지 않음
  - 모델이 없으면 죽지 않고 `모델 없음` 로그를 남긴 채 대기, 학습이 끝나면 재시작 없이 새 모델을 읽음
- **저장:** Docker Compose는 `anomaly_models` 볼륨, Helm(k3d)은 PVC — 컨테이너·파드를 재시작해도 유지됨. Compose에서 `docker compose down -v`를 하면 볼륨이 함께 지워지므로 재학습 필요
- **조회·관측:** `GET /anomalies?equipment_ids=&hours=`, Prometheus 메트릭(`mes_anomaly_score`, `mes_anomaly_threshold`, `mes_anomaly_detected_total` 등), Grafana "이상 점수 추이" 패널
- **경보 두 갈래:** 급변 경보(판정을 `anomaly_result`에 기록)와 열화 경보(`mes_drift_*` 메트릭·로그) — 아래 "급변 경보와 열화 경보"

## 평가 방법

1. 시뮬레이터를 `--anomaly-rate 0`으로 돌려 **정상 데이터만** 만들고, 그 구간(`--since`)만으로 학습
2. **별도 실행분**으로 `--anomaly-rate 0.2` 평가 데이터 생성
3. 시뮬레이터가 `POST /production-logs` 응답의 `(equipment_id, ts)`와 이상 여부를 라벨 파일(JSONL)에 기록 (DB에는 저장하지 않음)
4. `evaluate/evaluate.py`가 라벨과 워커 판정을 `(equipment_id, ts)`로 맞춰 설비별·전체 precision/recall/F1 계산, 학습·평가 구간이 겹치는지도 검사

threshold는 학습 데이터로만 정했고, 평가 데이터를 보고 조정하지 않았습니다. 설계를 바꾼 뒤에는 바꾸기 전 평가에 쓴 데이터가 아닌 **새 실행분**으로 공식 수치를 냅니다.

```bash
# 1) 학습용 (정상만) - 라벨도 남겨 이상 0건임을 기록
TRAIN_SINCE=$(date -u +%Y-%m-%dT%H:%M:%SZ)
(cd simulator && python3 simulate.py --api-url http://localhost:8001 --interval 0 --anomaly-rate 0 --max-ticks 300 --labels-file labels.jsonl)
docker compose run --rm anomaly-worker python train.py --since "$TRAIN_SINCE"

# 2) 평가용 - 별도 실행, 이상 비율 0.2 (워커가 새 모델을 읽을 때까지 10초 이상 기다린 뒤 실행)
(cd simulator && python3 simulate.py --api-url http://localhost:8001 --interval 0 --anomaly-rate 0.2 --max-ticks 500 --labels-file labels.jsonl)

# 3) 워커 판정이 끝난 뒤(10~20초) 평가 - 라벨 파일의 마지막 실행분 (--run-id로 지정 가능)
docker compose run --rm -v "$PWD/evaluate:/eval" -v "$PWD/simulator:/sim:ro" \
    anomaly-worker python /eval/evaluate.py --labels /sim/labels.jsonl

# 다른 모델로 같은 평가 데이터를 직접 채점 (DB 기록 없음, 모델 비교용)
docker compose run --rm -v "$PWD/evaluate:/eval" -v "$PWD/simulator:/sim:ro" \
    anomaly-worker python /eval/evaluate.py --labels /sim/labels.jsonl --score-with /models/c5
```

## v1의 recall이 낮았던 원인

Isolation Forest는 학습 범위를 벗어난 값을 "얼마나 멀리 벗어났는지"와 관계없이 같은 점수로 매깁니다.

- 설비마다 이상 데이터 106~108건의 점수가 **딱 두 값**으로만 나옴
  - 사이클타임·생산 수량만 벗어난 경우: 약 0.67~0.68 → threshold 미만 (놓침)
  - 불량률까지 벗어난 경우: 약 0.74~0.77 → 탐지
- 사이클타임을 정상의 1.3배, 2배, 3배로 늘려도 점수가 같음
- 정상(학습) 데이터의 최대 점수도 약 0.77이라, threshold 위치를 바꿔도 두 그룹을 깔끔히 나눌 수 없음

→ v2에서 학습 데이터 기준 범위 이탈 정도(robust z-score)를 점수에 결합해 해결.

## C안: 이동 구간 특징 (옵션, 기본 꺼짐)

최근 5구간 사이클타임 중앙값과 합산 불량률을 특징에 추가해 **점진적 열화**를 여러 구간을 모아 잡는 옵션입니다(`train.py --rolling-window 5`). 기존 시뮬레이터에는 급변 이상만 있어 효과를 볼 수 없으므로, 시뮬레이터에 점진적 열화 모드(`--drift-rate`, 20구간 동안 사이클타임 1.0→1.3배·불량률 3→10%)를 새 옵션으로 추가했습니다(기존 생성 방식은 그대로).

워커는 판정할 생산실적 앞의 K-1건 이력을 DB에서 함께 읽어 이동 구간 특징을 계산합니다. 열화 모드는 `--drift-rate`(설비별로 매 구간 열화가 시작될 확률), `--drift-len`(기본 20구간), `--drift-max`(기본 1.3배)로 조절하고, 열화 구간 전체를 이상(`anomaly_type: drift`)으로 라벨링합니다. `--drift-rate`를 주지 않으면 기존 생성 방식과 완전히 같습니다.

K=5, 열화 파라미터, 모델 구성은 평가 전에 고정했고, 설계 이후 새로 만든 두 실행분을 두 모델로 같은 데이터에서 채점했습니다(`--score-with`). v2 수치는 워커가 실제로 기록한 판정으로 계산한 결과와 일치합니다.

| 평가 실행분 | 모델 | Precision | Recall | F1 | FP | FN |
|---|---|---|---|---|---|---|
| 급변 이상 (`--anomaly-rate 0.2`, 05:36:44~, 이상 19.5%) | v2 | 0.942 | 1.000 | **0.970** | 18 | 0 |
| 급변 이상 (`--anomaly-rate 0.2`, 05:36:44~, 이상 19.5%) | v2 + C | 0.756 | 1.000 | 0.861 | 94 | 0 |
| 점진적 열화 (`--drift-rate 0.02`, 05:37:01~, 이상 31.1%) | v2 | 0.945 | 0.407 | 0.569 | 11 | 277 |
| 점진적 열화 (`--drift-rate 0.02`, 05:37:01~, 이상 31.1%) | v2 + C | 0.812 | 0.612 | **0.698** | 66 | 181 |

열화 진행도별 recall (열화 실행분):

| 열화 진행도 | 0~25% | 25~50% | 50~75% | 75~100% |
|---|---|---|---|---|
| v2 | 0.01 | 0.08 | 0.44 | 0.93 |
| v2 + C | 0.03 | 0.31 | **0.95** | 1.00 |

- 장점: 점진적 열화를 더 일찍 잡음 (진행도 50~75% 구간 recall 0.44 → 0.95). 진행도 25% 미만은 두 모델 모두 거의 못 잡음(정상 변동 범위 안)
- 대가: 이상 직후 구간으로 경보가 번져 오탐 증가. 급변 실행분에서 C의 오탐 94건 중 86건이 급변 직후 4구간 이내(v2는 18건 중 11건), 열화 실행분에서도 C의 오탐 66건 중 50건이 열화 종료 직후 4구간 이내. 라벨이 구간 단위라 "이상 직후의 늦은 경보"도 오탐으로 계산됨

```bash
# C안 모델을 별도 디렉터리에 학습 (TRAIN_SINCE/TRAIN_UNTIL = 정상 전용 실행의 시작/끝. 이후 이상 섞인 데이터가 쌓였으므로 --until 필수)
docker compose run --rm anomaly-worker python train.py --since "$TRAIN_SINCE" --until "$TRAIN_UNTIL" --rolling-window 5 --model-dir /models/c5
(cd simulator && python3 simulate.py --api-url http://localhost:8001 --interval 0 --anomaly-rate 0 --drift-rate 0.02 --max-ticks 500 --labels-file labels.jsonl)
docker compose run --rm -v "$PWD/evaluate:/eval" -v "$PWD/simulator:/sim:ro" \
    anomaly-worker python /eval/evaluate.py --labels /sim/labels.jsonl --score-with /models/c5
```
- 그래서 급변 판정(DB 기록)은 v2로 유지하고, C안은 별도의 열화 경보로 분리

## 급변 경보와 열화 경보

| | 급변 경보 | 열화 경보 |
|---|---|---|
| 모델 | v2 (구간 1건 특징) | v2 + 이동 구간 특징 (C안) |
| 결과 | `anomaly_result` → `/anomalies` | 경보 시작/해제 → `drift_alarm` → `/drift-alarms` (CSV 가능), 판정 건별 점수는 메트릭(`mes_drift_*`) |
| Grafana | 이상 점수 추이, 이상 탐지 횟수 | 열화 점수 추이, 열화 경보 상태 |

![이상탐지 패널]({{ '/assets/images/grafana-anomaly-drift.png' | relative_url }})

*같은 실행분의 이상탐지 패널. 왼쪽 위는 급변 탐지(v2) 점수, 왼쪽 아래는 열화 감시(C안) 점수이고, 오른쪽 아래는 설비별 경보 상태와 최근 1시간 경보 횟수입니다 (실행이 끝난 뒤라 모두 해제된 상태).*

- 급변 경보 모델은 `/models`, 열화 경보 모델은 `/models/drift`(C안, K=5). 열화 모델이 없으면 열화 감시만 건너뜀
- 열화 경보 이력은 `drift_alarm` 테이블에 경보 1건 = 1행(시작 시각·점수·threshold, 해제 시각)으로 남고 `/drift-alarms`로 조회합니다. 워커가 재시작되면 진행 중(해제 시각 없음) 경보로 상태를 복원해, 같은 경보를 다시 만들거나 해제 기록을 놓치지 않습니다 (연속 판정 횟수는 0부터 다시 셈). 설비당 진행 중 경보는 부분 유일 인덱스로 하나만 허용
  - 확인 (2026-09-29, compose): 열화 실행분(`--drift-rate 0.05`, 300구간)에서 DB 기록 21건 = 워커 로그 "경보 시작" 21건. 진행 중 경보 2건(EQ-001·EQ-003)이 남은 상태에서 워커 재시작 → "상태 복원" 로그 → 정상 데이터 30구간 후 두 경보 모두 해제, 행 수 21 그대로
- 급변 탐지기가 잡은 생산실적은 열화 경보 판단을 **보류**합니다 (급변 1건의 중복 경보 방지 + 급변 탐지기도 잡을 만큼 진행된 열화 후반에 열화 경보가 꺼지지 않게).
- (3차 이후 현재 규칙은 아래 "3차" 참고) 열화 경보는 **2구간 연속** 열화 판정이면 시작, **3구간 연속** 정상이면 해제 (히스테리시스, `DRIFT_RAISE_AFTER`/`DRIFT_CLEAR_AFTER`). 평가 전에 고정 — 시작은 20구간 열화 대비 1구간 지연 허용, 해제는 이동 구간(5)의 절반 넘게 정상일 때

### 1차: 급변 판정 건을 열화에서 제외

시연 실행분에서 열화 경보 시작 30번 중 18번이 급변 때문이었습니다(열화 모델도 현재 구간 특징을 쓰기 때문). 급변 판정 건을 열화에서 제외하는 규칙을 넣고 새 실행분(`--interval 1 --anomaly-rate 0.05 --drift-rate 0.03 --max-ticks 150`, 450건, 급변 39·열화 134건)으로 확인했습니다. 워커 로그의 경보 시작 수(30)와 오프라인 분석이 일치합니다.

| | 열화 경보 시작 | 급변 때문 | 열화 중 | 급변 직후 4구간 | 그 외 정상 | 열화 에피소드 감지 | 첫 경보(중앙값) |
|---|---|---|---|---|---|---|---|
| 규칙 없음 | 45 | 28 | 12 | 2 | 3 | 7/8 | 4번째 구간 |
| 급변 제외 | 30 | 0 | 18 | 6 | 6 | 7/8 | 6번째 구간 |

### 2차: 깜빡임 완화 (히스테리시스 + 급변 구간 판단 보류)

1차 결과에서 열화 경보가 에피소드 안에서 여러 번 켜졌다 꺼져, 연속 조건(2/3)을 넣었습니다. 이를 평가한 실행분(06:01:09~)에서 **열화 후반(진행도 75~100%)의 91%를 급변 탐지기도 이상으로 잡고**, 1차 규칙(급변 판정 = 열화 아님)이 이를 정상으로 취급해 **열화 도중 경보가 꺼졌다가 열화가 끝난 직후 다시 켜지는** 문제가 드러났습니다(끝까지 진행된 에피소드 26개 중 24개). 그래서 급변 판정 구간을 "판단 보류"로 바꾸고 **또 다른 새 실행분**(`--interval 0 --anomaly-rate 0.05 --drift-rate 0.03 --max-ticks 500`, 06:03:58~, 1500건, 급변 71·열화 409건, 에피소드 19개)으로 모든 규칙을 같은 데이터에서 비교했습니다.

| 시작/해제 연속 조건 | 급변 구간 처리 | 경보 시작 | 열화 중 | 급변 직후 4구간 | 열화 직후 4구간 | 그 외 정상 | 에피소드 감지 | 에피소드당 경보 | 첫 경보(중앙값) | 도중 해제된 에피소드 | 정상인데 경보 중인 구간 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1/1 | 정상 취급 | 76 | 45 | 8 | 14 | 9 | 19/19 | 2.05 | 8/20 | 19 | 59 |
| 2/3 | 정상 취급 | 41 | 20 | 5 | 13 | 3 | 17/19 | 1.06 | 9/20 | 16 | 76 |
| **2/3 (적용)** | **판단 보류** | **25** | 20 | 0 | 2 | 3 | **18/19** | **1.00** | 9/20 | **0** | 99 |

- 경보 시작 76 → 25번, 에피소드당 경보 2.05 → 1.00번, 도중 해제 19 → 0개. 규칙을 만든 06:01:09 실행분에서도 같은 경향(경보 99 → 31, 에피소드 감지 26/27, 도중 해제 26 → 2). 워커 로그의 경보 시작 수(25)와 오프라인 분석 일치
- 대가: 열화가 끝난 뒤에도 경보가 평균 약 5구간 더 켜져 있음("정상인데 경보 중인 구간" 59 → 99). 열화 초반(진행도 25% 미만)은 여전히 거의 못 잡음

### 3차: 해제 지연 줄이기 + 열화 초반 감지 (2026-10-01)

2차에서 남은 두 문제의 원인을 이렇게 봤습니다.

- **해제가 늦음:** 열화 모델의 이동 구간 특징(최근 5구간 중앙값·합산 불량률)은 열화가 끝난 뒤에도 4구간 동안 높게 남습니다. 여기에 3구간 연속 정상 조건까지 더해져 해제가 늦어집니다.
- **초반을 못 잡음:** 정상 사이클타임의 변동(표준편차 5%)에 비해 열화 초반의 상승이 작습니다(진행도 25%에서 +7.5%, 약 1.5σ). 구간 하나만 보는 판정으로는 정상 변동과 구분되지 않습니다.

그래서 두 장치를 추가했습니다. 둘 다 이미 학습된 모델 번들의 robust 중앙값·척도(정상 데이터 기준)로 현재 구간 사이클타임 z를 계산하므로, 재학습이 필요 없습니다.

| 장치 | 동작 | 설정 (빈 값이면 끔) |
|---|---|---|
| (A) 현재 구간 z로 해제 | 경보 중에는 모델 판정 대신 "사이클타임 z < 1.5"를 정상으로 보고, 2구간 연속이면 해제 | `DRIFT_CLEAR_Z=1.5`, `DRIFT_CLEAR_AFTER=2` |
| (B) CUSUM으로 시작 | 단측 CUSUM `S = max(0, S + min(z, 4) − k)`가 h를 넘으면 경보 시작 (기존 "2구간 연속 열화 판정"과 OR). 작은 상승이 계속되면 쌓이고, 정상 변동(z ≤ k)은 쌓이지 않음. 급변 구간은 더하지 않고, 경보 시작·해제 때 0으로 초기화 | `DRIFT_CUSUM_K=1.0`, `DRIFT_CUSUM_H=4.0` |

**절차.** 경보 정책을 오프라인으로 재생하는 평가 도구 `evaluate/drift_alarm_eval.py`를 만들었습니다. 워커와 같은 모델·`DriftAlarm` 코드를 써서, 라벨의 열화 에피소드 기준으로 지표를 계산합니다. 실행분은 세 종류로 나눴습니다.

1. **검증 실행분**에서 후보를 비교해 값을 정했습니다.
   - 열화 실행분: `--interval 0 --anomaly-rate 0.05 --drift-rate 0.03 --max-ticks 500`
   - 정상 위주 실행분: `--anomaly-rate 0.03 --drift-rate 0`, 3000건. 서버 시뮬레이터와 비슷한 조건에서 오경보를 확인했습니다.
2. 값을 고정한 뒤 새로 만든 **평가 실행분**으로 결과를 보고했습니다.
3. 마지막으로 **워커에 적용**한 뒤 새 실행분으로 실제 워커 기록과 오프라인 재생 결과를 비교했습니다.

검증 실행분(열화, 1500건, 에피소드 29개)에서 비교한 후보 일부입니다.

| 정책 | 첫 경보(중앙값) | 도중 해제 | 정상인데 경보 중 | 종료 후 해제까지(중앙값/평균) |
|---|---|---|---|---|
| 기존 2/3 | 11/20 | 3 | 143 | 4 / 4.6 |
| A: z < 1.5, 2구간 | 11/20 | 2 | 51 | 1 / 1.5 |
| A: z < 1.0, 2구간 | 11/20 | 2 | 80 | 1 / 2.3 |
| B: k = 0.5, h = 4 | **6/20** | 11 | 147 | 4 / 4.6 |
| B: k = 1, h = 4 | 8/20 | 3 | 143 | 4 / 4.6 |
| **A + B (적용)** | **8/20** | 3 | **51** | **1 / 1.5** |

- k = 0.5는 더 일찍 잡지만, 일찍 켜진 경보가 모델 판정으로 꺼졌다 켜지기를 반복했습니다(도중 해제 11). 그래서 k = 1을 골랐습니다.
- 정상 위주 실행분(3000건)에서는 모든 후보의 "그 외 정상" 오경보가 3건으로 같았습니다. CUSUM이 오경보를 늘리지 않았고, 정상인데 경보 중인 구간은 18 → 10으로 줄었습니다.

**평가 실행분** (`20261001T034556Z`, 1500건, 이상 561건, 에피소드 26개 — 값을 고정한 뒤 생성):

| 정책 | 경보 시작 | 열화 중 | 급변 직후 4구간 | 열화 직후 4구간 | 그 외 정상 | 에피소드 감지 | 에피소드당 경보 | 첫 경보(중앙값) | 도중 해제 | 정상인데 경보 중 | 종료 후 해제까지(중앙값/평균) | 정상 1000구간당 오경보 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 기존 2/3 | 27 | 22 | 1 | 3 | 1 | 21/26 | 1.05 | 10/20 | 3 | 109 | 4 / 4.2 | 1.1 |
| A만 | 27 | 22 | 1 | 3 | 1 | 21/26 | 1.05 | 10/20 | 2 | 45 | 1 / 1.7 | 1.1 |
| B만 | 27 | 26 | 0 | 0 | 1 | 26/26 | 1.00 | 9/20 | 3 | 110 | 4 / 4.0 | 1.1 |
| **A + B (적용)** | 27 | 26 | 0 | 0 | 1 | **26/26** | 1.00 | **9/20** | **2** | **41** | **1 / 1.5** | 1.1 |

- **해제 지연:** 열화가 끝난 뒤 경보가 꺼지기까지 중앙값 4 → 1구간, 정상인데 경보 중인 구간 109 → 41
- **감지:** 놓친 에피소드 5개를 CUSUM이 잡아 21/26 → 26/26. "열화가 끝난 직후에야 켜지는 늦은 경보" 3 → 0
- **초반 감지는 소폭 개선:** 첫 경보 중앙값 10 → 9번째 구간(검증 실행분에서는 11 → 8). 진행도 25% 미만은 여전히 대부분 놓칩니다
- 오경보는 그대로(정상 1000구간당 1.1)
- **워커 적용 확인:** 새 실행분(`--interval 1`, 450건, 워커가 여러 판정 주기에 나눠 처리)에서 워커가 `drift_alarm`에 기록한 경보 시작은 6건이었습니다. 같은 실행분을 오프라인으로 재생한 결과도 6건으로 일치했습니다.

```bash
docker compose run --rm -v "$PWD/evaluate:/eval" -v "$PWD/simulator:/sim:ro" anomaly-worker \
    python /eval/drift_alarm_eval.py --labels /sim/labels.jsonl --run-id <실행분> \
    --policy "기존=2/3" --policy "적용=2/2,clear_z=1.5,k=1,h=4"
```

## 알려진 한계

- 가상 데이터 기준이며, 시뮬레이터의 이상 패턴(사이클타임 2~3.5배 + 불량률 20~40%)은 실제 고장 양상보다 단순함
- 특징이 단순함 (기본은 생산실적 1건 단위 3개, 옵션으로 이동 구간 2개. 센서 데이터 없음). 구간당 생산량이 적은 설비(EQ-001, 약 4~5개)는 불량률이 0%/25%로 오가 변별력이 낮음
- recall 1.000(급변)은 시뮬레이터 이상이 정상에서 매우 멀리 떨어진 쉬운 이상이라 나온 수치. 점진적 열화 초반(진행도 25% 미만)은 거의 못 잡음
- 열화 경보는 열화 종료 후 평균 1.5구간 더 켜져 있음(3차 이전 4.2). 해제와 CUSUM은 사이클타임만 보고 불량률은 쓰지 않음. 판정 건별 열화 점수는 DB에 남지 않음 (경보 시작/해제 이력만 `drift_alarm`에 기록)
- `anomaly_result`에 생산실적 ID가 없어 `(equipment_id, ts)`로 같은 로그인지 판단 — 같은 설비·같은 ts 로그가 두 건 이상이면 한 건만 판정
- 설비별 모델이라 새 설비를 추가하거나 공정 조건이 바뀌면 재학습 필요 (자동 재학습 없음)
- 학습 데이터가 정상인지는 사람이 학습 구간을 지정해서 보장함
- Helm 차트(워커·Prometheus·Grafana 포함)는 k3d 로컬 검증까지만 했음

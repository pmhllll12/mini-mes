> **이 결과는 시뮬레이터가 만든 가상 데이터 기준이며 실제 설비 성능이 아니다.**

## 구조

`anomaly-worker`는 API와 분리된 별도 컨테이너입니다.

- **특징:** 생산실적 1건당 사이클타임, 구간당 생산 수량(`qty_good + qty_defect`), 불량률
- **모델(v2):** 설비별 Isolation Forest + 범위 이탈 robust z-score
  - `anomaly_score = max(if_score / if기준, z_score / z기준)`, `z_score` = 특징별 `|x - 중앙값| / (1.4826 × MAD)`의 최댓값
  - 두 기준과 최종 threshold는 모두 학습(정상) 데이터 점수의 99% 분위수 → 학습 범위 밖으로 멀어질수록 점수가 계속 커짐
- **워커:** 10초마다 아직 판정하지 않은 최근 24시간 생산실적을 추론해 `anomaly_result`에 기록
  - `anomaly_result`에 log_id가 없어(스키마 변경 없음) 생산실적의 `ts`를 그대로 쓰고, `(equipment_id, ts)`로 중복 기록을 막음
  - 학습에 쓴 구간(`train_end` 이전)은 추론하지 않음
  - 모델이 없으면 죽지 않고 `모델 없음` 로그를 남긴 채 대기, 학습이 끝나면 재시작 없이 새 모델을 읽음
- **저장:** Docker Compose는 `anomaly_models` 볼륨, Helm(k3d)은 PVC — 컨테이너·파드를 재시작해도 유지됨. Compose에서 `docker compose down -v`를 하면 볼륨이 함께 지워지므로 재학습 필요
- **조회·관측:** `GET /anomalies?equipment_ids=&hours=`, Prometheus 메트릭(`mes_anomaly_score`, `mes_anomaly_threshold`, `mes_anomaly_detected_total` 등), Grafana "이상 점수 추이" 패널

## 평가 방법

1. 시뮬레이터를 `--anomaly-rate 0`으로 돌려 **정상 데이터만** 만들고, 그 구간(`--since`)만으로 학습
2. **별도 실행분**으로 `--anomaly-rate 0.2` 평가 데이터 생성
3. 시뮬레이터가 `POST /production-logs` 응답의 `(equipment_id, ts)`와 이상 여부를 라벨 파일(JSONL)에 기록 (DB에는 저장하지 않음)
4. `evaluate/evaluate.py`가 라벨과 워커 판정을 `(equipment_id, ts)`로 맞춰 설비별·전체 precision/recall/F1 계산, 학습·평가 구간이 겹치는지도 검사

threshold는 학습 데이터로만 정했고, 평가 데이터를 보고 조정하지 않았습니다.

## v1의 recall이 낮았던 원인

Isolation Forest는 학습 범위를 벗어난 값을 "얼마나 멀리 벗어났는지"와 관계없이 같은 점수로 매깁니다.

- 설비마다 이상 데이터 106~108건의 점수가 **딱 두 값**으로만 나옴
  - 사이클타임·생산 수량만 벗어난 경우: 약 0.67~0.68 → threshold 미만 (놓침)
  - 불량률까지 벗어난 경우: 약 0.74~0.77 → 탐지
- 사이클타임을 정상의 1.3배, 2배, 3배로 늘려도 점수가 같음
- 정상(학습) 데이터의 최대 점수도 약 0.77이라, threshold 위치를 바꿔도 두 그룹을 깔끔히 나눌 수 없음

→ v2에서 학습 데이터 기준 범위 이탈 정도(robust z-score)를 점수에 결합해 해결.

## C안: 이동 구간 특징 (옵션, 기본 꺼짐)

최근 5구간 사이클타임 중앙값과 합산 불량률을 특징에 추가해 **점진적 열화**를 여러 구간을 모아 잡는 옵션입니다(`train.py --rolling-window 5`). 기존 시뮬레이터에는 급변 이상만 있어 효과를 볼 수 없으므로, 시뮬레이터에 점진적 열화 모드(`--drift-rate`, 20구간 동안 사이클타임 1.0→1.3배·불량률 3→10%)를 새 옵션으로 추가했습니다(기존 생성 방식은 그대로).

파라미터는 평가 전에 고정했고, 설계 이후 새로 만든 두 실행분을 두 모델로 같은 데이터에서 채점했습니다.

| 평가 실행분 | 모델 | Precision | Recall | F1 |
|---|---|---|---|---|
| 급변 이상 (이상 19.5%) | v2 | 0.942 | 1.000 | **0.970** |
| 급변 이상 (이상 19.5%) | v2 + C | 0.756 | 1.000 | 0.861 |
| 점진적 열화 (이상 31.1%) | v2 | 0.945 | 0.407 | 0.569 |
| 점진적 열화 (이상 31.1%) | v2 + C | 0.812 | 0.612 | **0.698** |

- 열화 진행도 50~75% 구간 recall: v2 0.44 → v2+C 0.95 (더 일찍 잡음). 진행도 25% 미만은 두 모델 모두 거의 못 잡음
- 대가: 이상 직후 구간으로 경보가 번져 오탐 증가 (급변 실행분 C의 오탐 94건 중 86건이 급변 직후 4구간 이내)
- 그래서 급변 판정(DB 기록)은 v2로 유지하고, C안은 별도의 열화 경보로 분리

## 급변 경보와 열화 경보

| | 급변 경보 | 열화 경보 |
|---|---|---|
| 모델 | v2 (구간 1건 특징) | v2 + 이동 구간 특징 (C안) |
| 결과 | `anomaly_result` → `/anomalies` | 메트릭(`mes_drift_*`)·로그만 (스키마 유지로 DB 미기록) |
| Grafana | 이상 점수 추이, 이상 탐지 횟수 | 열화 점수 추이, 열화 경보 상태 |

- 급변 탐지기가 잡은 생산실적은 열화 경보 판단을 **보류**합니다 (급변 1건의 중복 경보 방지 + 급변 탐지기도 잡을 만큼 진행된 열화 후반에 열화 경보가 꺼지지 않게).
- 열화 경보는 **2구간 연속** 열화 판정이면 시작, **3구간 연속** 정상이면 해제 (히스테리시스, 평가 전 고정).

검증 실행분(1500건, 급변 71·열화 409건, 에피소드 19개)에서 같은 데이터로 비교:

| 규칙 | 경보 시작 | 에피소드 감지 | 에피소드당 경보 | 도중 해제된 에피소드 | 정상인데 경보 중인 구간 |
|---|---|---|---|---|---|
| 연속 조건 없음, 급변=정상 취급 | 76 | 19/19 | 2.05 | 19 | 59 |
| 2/3, 급변=정상 취급 | 41 | 17/19 | 1.06 | 16 | 76 |
| **2/3, 급변=판단 보류 (적용)** | **25** | **18/19** | **1.00** | **0** | 99 |

"판단 보류" 규칙은 이전 실행분에서 급변 탐지기가 열화 후반의 91%를 잡아 열화 경보가 도중에 꺼지는 문제를 보고 만들었고, 효과는 그 뒤 새로 만든 위 실행분으로 확인했습니다. 대가로 열화가 끝난 뒤에도 경보가 평균 약 5구간 더 켜져 있습니다.

## 알려진 한계

- 가상 데이터 기준이며, 시뮬레이터의 이상 패턴(사이클타임 2~3.5배 + 불량률 20~40%)은 실제 고장 양상보다 단순함
- 특징이 단순함 (생산실적 1건 단위 3개 특징, 추세·센서 데이터 없음). 구간당 생산량이 적은 설비는 불량률 변별력이 낮음
- 설비별 모델이라 새 설비를 추가하거나 공정 조건이 바뀌면 재학습 필요 (자동 재학습 없음)
- 학습 데이터가 정상인지는 사람이 학습 구간을 지정해서 보장함
- Helm 차트의 워커는 k3d 로컬 검증까지만 했고, 차트에 Prometheus/Grafana가 없어 클러스터에서는 메트릭을 수집하지 않음
